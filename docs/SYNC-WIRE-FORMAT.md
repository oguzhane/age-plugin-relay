# Sync Wire Format Reference

Complete HTTP request/response bodies for the sync flow. Two actors: **Plugin** and **Relay-Server**. One round-trip: the plugin POSTs an encrypted unwrap request, the relay-server decrypts, unwraps, and responds immediately with the sealed file key.

All interactions use `POST` with `Content-Type: application/json` (request) and either `application/json` or `text/event-stream` (response).

---

## 1. Plugin → Relay-Server: unwrap request

### Request

```json
{
  "version": 1,
  "action": "unwrap",
  "stream": false,
  "intent_id": "a3f12c4e8b9d6f0a1b2c3d4e5f6a7b8c",
  "tag": "QPg24g",
  "expires_at": 1715350800,
  "intent_claim_pub": "<base64: Ed25519 public key>",
  "encrypted_payload": "<base64: age-encrypted InnerRequestPayload>"
}
```

| Field | Type | Description |
|---|---|---|
| `version` | int | Always `1` |
| `action` | string | `"unwrap"` |
| `stream` | bool | `true` to request SSE response. `false` or omitted for JSON |
| `intent_id` | string | 16 random bytes, hex-encoded (32 chars). Generated by plugin |
| `tag` | string | `base64(SHA-256(unwrap_recipient)[:4])`. Routing tag |
| `expires_at` | int64 | Unix timestamp (seconds). Plugin sets `now + timeout` |
| `intent_claim_pub` | string | Ed25519 public key (base64 raw standard). Present for format consistency with async flow. Not verified in sync mode — see note below |
| `encrypted_payload` | string | Base64 age ciphertext. Encrypted to relay-server's recipient |

The request body is a `RelayRequest` — the same struct used in the async flow. The relay-server only accepts `action: "unwrap"`.

### Inside `encrypted_payload` (InnerRequestPayload)

Encrypted with `age.Encrypt` to the relay-server's age recipient (the `unwrap_recipient` from config). The relay-server decrypts with its local identity.

```json
{
  "nonce": "deadbeef01020304deadbeef01020304",
  "outer_hash": "<SHA-256 hex, 64 chars>",
  "expires_at": 1715350800,
  "stanzas": [
    {
      "type": "X25519",
      "args": ["ephemeral-share"],
      "body": "<base64 raw std>"
    }
  ],
  "ephemeral_key": "age1qqnv7...plugin's ephemeral public key...",
  "intent_claim_secret": "<base64: Ed25519 private key seed>"
}
```

| Field | Type | Description |
|---|---|---|
| `nonce` | string | 16 random bytes, hex-encoded (32 chars). Ensures ciphertext uniqueness |
| `outer_hash` | string | SHA-256 hex (64 chars). Covers every envelope field outside `encrypted_payload` — see [Complete Outer Field Binding](ARCHITECTURE.md#35-outer-hash-construction) |
| `expires_at` | int64 | Duplicated from outer envelope. Used for expiry check after decryption |
| `stanzas` | array | The age stanzas from the original `age.Encrypt` operation |
| `ephemeral_key` | string | Plugin's ephemeral age X25519 public key (`age1...`). Response is encrypted to this |
| `intent_claim_secret` | string | Ed25519 private key seed (base64 raw standard). Present for format consistency. Not used in sync mode |

Each stanza:

| Field | Type | Description |
|---|---|---|
| `type` | string | Stanza type (e.g., `"X25519"`) |
| `args` | string[] | Stanza arguments |
| `body` | string | Stanza body, base64 raw standard encoded |

**Outer hash computation:**

> **Complete Outer Field Binding:** The outer hash MUST include every envelope field outside `encrypted_payload`. This is a fundamental protocol invariant — see [ARCHITECTURE.md §3.5](ARCHITECTURE.md#35-outer-hash-construction).

> **Sealed Action Binding:** Every `action` value (fulfill, reject, etc.) MUST carry an `encrypted_payload` with an outer hash that the recipient verifies. No action is exempt — a cleartext-only envelope can be forged by the broker. See [ARCHITECTURE.md §3.5](ARCHITECTURE.md#35-outer-hash-construction).

```
SHA-256("{version}.{action}.{stream}.{intent_id}.{tag}.{expires_at}.{intent_claim_pub}")
```

Example:

```
SHA-256("1.unwrap.0.a3f12c4e8b9d6f0a1b2c3d4e5f6a7b8c.QPg24g.1715350800.AAAA...")
```

> **Sync flow note:** In the sync flow, the relay-server handles both decrypt and respond in a single process. There is no third-party fulfill step, so `intent_claim_sig` verification is not needed. The `intent_claim_pub` is included in the outer hash for consistency with the async wire format, and `intent_claim_secret` is present in the inner payload for the same reason. See [Intent Claim](INTENT-CLAIM.md) for the full design.

## 2. Relay-Server → Plugin: response

The relay-server responds in one of two formats based on the `stream` field in the request.

### 2a. JSON response (`stream: false` or omitted)

**Content-Type:** `application/json`

#### Success — 200 OK

```json
{
  "version": 1,
  "action": "fulfill",
  "intent_id": "a3f12c4e8b9d6f0a1b2c3d4e5f6a7b8c",
  "encrypted_payload": "<base64: age-encrypted InnerResponsePayload>"
}
```

The success response uses the same `RelayRequest` envelope shape and `action: "fulfill"` as the async flow's operator fulfill body. This unified format means the plugin always parses the same structure regardless of sync or async mode.

#### Error — 400 Bad Request

Returned for: invalid JSON, unsupported version, unsupported action, missing `encrypted_payload`, decryption failure, outer hash mismatch, expiry, invalid stanza body.

```json
{
  "error": "decrypting payload: ..."
}
```

```json
{
  "error": "payload verification: ..."
}
```

```json
{
  "error": "missing encrypted_payload"
}
```

```json
{
  "error": "unsupported protocol version: 2"
}
```

```json
{
  "error": "unsupported action: poll"
}
```

```json
{
  "error": "invalid JSON: ..."
}
```

#### Error — 401 Unauthorized

Returned when auth token is required but missing or wrong.

```json
{
  "error": "unauthorized"
}
```

#### Reject — 200 OK

Returned when no identity can unwrap the stanzas. Uses the same `RelayRequest` envelope shape as fulfill, with `action: "reject"` and an `encrypted_payload` containing an `InnerResponsePayload` with empty `file_key`. The plugin decrypts and verifies the outer hash to confirm authenticity.

```json
{
  "version": 1,
  "action": "reject",
  "intent_id": "a3f12c4e8b9d6f0a1b2c3d4e5f6a7b8c",
  "encrypted_payload": "<base64: age-encrypted InnerResponsePayload with empty file_key>"
}
```

Inside `encrypted_payload`:

```json
{
  "nonce": "1a2b3c4d5e6f7a8b1a2b3c4d5e6f7a8b",
  "outer_hash": "<SHA-256 hex of '1.reject.a3f12c4e8b9d6f0a1b2c3d4e5f6a7b8c'>",
  "file_key": ""
}
```

#### Error — 405 Method Not Allowed

Returned for non-POST requests.

```json
{
  "error": "method not allowed"
}
```

#### Error — 500 Internal Server Error

Returned when response payload building or sealing fails.

```json
{
  "error": "building response payload"
}
```

```json
{
  "error": "sealing response"
}
```

### 2b. SSE response (`stream: true`)

**Content-Type:** `text/event-stream`
**Cache-Control:** `no-cache`
**Connection:** `keep-alive`
**Status Code:** Always `200 OK` (errors are delivered as SSE events)

SSE is for long-running relay scenarios (approval flows, remote YubiKey touch). The connection stays open through proxies and load balancers.

#### Success event

```
event: result
data: {"version":1,"action":"fulfill","intent_id":"a3f12c4e8b9d6f0a1b2c3d4e5f6a7b8c","encrypted_payload":"<base64: age-encrypted InnerResponsePayload>"}

```

The `data` field is a JSON-serialized `RelayRequest` envelope (same shape as the JSON success response).

#### Error event

```
event: error
data: {"error":"some error message"}

```

The `data` field is a JSON-serialized `RelayResponse` with the `error` field set. Used for errors other than no-matching-identity (e.g., decryption failure, invalid payload).

#### Reject event

```
event: reject
data: {"version":1,"action":"reject","intent_id":"a3f12c4e8b9d6f0a1b2c3d4e5f6a7b8c","encrypted_payload":"<base64>"}

```

The `data` field is a JSON-serialized `RelayRequest` envelope with `action: "reject"` and an `encrypted_payload` containing an `InnerResponsePayload` with empty `file_key`. The plugin decrypts and verifies the outer hash. Sent when no identity can unwrap the stanzas.

#### Heartbeat comments

The server may send SSE comments as heartbeats to keep the connection alive:

```
: heartbeat

```

The plugin ignores lines starting with `:`.

#### Plugin SSE parsing

The plugin reads the stream line by line:

1. Lines starting with `:` → heartbeat, ignored
2. `event: <type>` → sets the event type
3. `data: <json>` → accumulates event data
4. Empty line → dispatches the event:
   - `event: result` → parse `RelayRequest` envelope, extract file key
   - `event: reject` → parse `RelayRequest` envelope, return reject error
   - `event: error` → parse `RelayResponse`, return error
   - Unknown event type → ignored (forward compatibility)
5. Stream ends without result/reject/error → error

## 3. Inside `encrypted_payload` (InnerResponsePayload)

Encrypted with `age.Encrypt` to the plugin's ephemeral recipient (`ephemeral_key` from the request). The plugin decrypts with its ephemeral identity.

```json
{
  "nonce": "1a2b3c4d5e6f7a8b1a2b3c4d5e6f7a8b",
  "outer_hash": "<SHA-256 hex, 64 chars>",
  "file_key": "<base64 raw std: 16-byte age file key>"
}
```

| Field | Type | Description |
|---|---|---|
| `nonce` | string | 16 random bytes, hex-encoded (32 chars). Ensures ciphertext uniqueness |
| `outer_hash` | string | SHA-256 hex (64 chars). Covers every envelope field outside `encrypted_payload` — see [Complete Outer Field Binding](ARCHITECTURE.md#35-outer-hash-construction) |
| `file_key` | string | The unwrapped age file key, base64 raw standard encoded (16 bytes) |

**Outer hash computation** (covers all response envelope fields outside `encrypted_payload`):

```
SHA-256("{version}.{action}.{intent_id}")
```

Example:

```
SHA-256("1.fulfill.a3f12c4e8b9d6f0a1b2c3d4e5f6a7b8c")
```

---

## 4. Plugin verification steps

After receiving the response (JSON or SSE `result` event):

1. Parse the `RelayRequest` envelope — extract `action` and `encrypted_payload`.
2. `age.Decrypt(encrypted_payload, ephemeral_identity)` → inner response JSON.
3. Parse `InnerResponsePayload`.
4. Recompute `SHA-256("{action}." + intent_id)` using the action from the envelope and the plugin's own stored `intent_id`.
5. Compare against `outer_hash` — mismatch = tamper = fail.
6. Base64-decode `file_key` → 16-byte age file key.
7. Discard ephemeral keypair.

---

## 5. Relay-server processing steps

After receiving the request:

1. Verify auth token (if configured). Reject with 401 if invalid.
2. Parse `RelayRequest` from JSON body.
3. Validate `version == 1` and `action == "unwrap"`.
4. Validate `encrypted_payload` is present.
5. `age.Decrypt(encrypted_payload, identity)` → `InnerRequestPayload`.
6. Check `expires_at` — reject if in the past.
7. Recompute `SHA-256("1.unwrap." + stream + "." + intent_id + "." + tag + "." + expires_at + "." + intent_claim_pub)` where `stream` is `"0"` or `"1"`.
8. Compare against `outer_hash` — mismatch = reject.
9. Decode stanzas from inner payload.
10. Try each local identity: `identity.Unwrap(stanzas)` → file key. If no identity succeeds → build `InnerResponsePayload{nonce, outer_hash, file_key:""}` where `outer_hash = SHA-256("1.reject." + intent_id)`, seal to ephemeral key, return `RelayRequest{version:1, action:"reject", intent_id, encrypted_payload}` as JSON (HTTP 200) or SSE `reject` event.
11. Build `InnerResponsePayload`: `{nonce, outer_hash, file_key}` where `outer_hash = SHA-256("1.fulfill." + intent_id)`.
12. `age.Encrypt(inner_response, ephemeral_key)` → sealed `encrypted_payload`.
13. Return `RelayRequest` envelope as JSON (HTTP 200) or SSE `result` event.

---

## 6. Error status code summary

| Status | Condition | Body |
|---|---|---|
| 200 OK | Unwrap succeeded (JSON mode) | `{"version":1,"action":"fulfill","intent_id":"...","encrypted_payload":"..."}` |
| 200 OK | No identity could unwrap (JSON mode) | `{"version":1,"action":"reject","intent_id":"...","encrypted_payload":"..."}` |
| 200 OK | Unwrap succeeded (SSE mode) | `event: result\ndata: {"version":1,"action":"fulfill",...}` |
| 200 OK | No identity could unwrap (SSE mode) | `event: reject\ndata: {"version":1,"action":"reject",...}` |
| 200 OK | Unwrap failed (SSE mode) | `event: error\ndata: {"error": "..."}` |
| 400 | Invalid JSON, bad version, bad action, missing field, decrypt/verify failure | `{"error": "..."}` |
| 401 | Auth token missing or wrong | `{"error": "unauthorized"}` |
| 405 | Non-POST method | `{"error": "method not allowed"}` |
| 500 | Internal: payload build or seal failure | `{"error": "..."}` |

Note: In SSE mode, the HTTP status is always `200 OK`. Success, reject, and error are delivered as SSE events (`result`, `reject`, or `error`). The plugin distinguishes them by event type, not status code.

## Go Types

Request (plugin sends):

```go
// relay/client.go
type RelayRequest struct {
    Version          int    `json:"version"`
    Action           string `json:"action"`
    Stream           bool   `json:"stream,omitempty"`
    IntentID         string `json:"intent_id,omitempty"`
    Tag              string `json:"tag,omitempty"`
    ExpiresAt        int64  `json:"expires_at,omitempty"`
    IntentClaimPub   string `json:"intent_claim_pub,omitempty"`
    IntentClaimSig   string `json:"intent_claim_sig,omitempty"`
    EncryptedPayload string `json:"encrypted_payload,omitempty"`
}
```

Response (relay-server returns on success — same `RelayRequest` envelope):

```go
// relay/client.go — success uses RelayRequest shape
type RelayRequest struct {
    Version          int    `json:"version"`
    Action           string `json:"action"`
    Stream           bool   `json:"stream,omitempty"`
    IntentID         string `json:"intent_id,omitempty"`
    Tag              string `json:"tag,omitempty"`
    ExpiresAt        int64  `json:"expires_at,omitempty"`
    IntentClaimPub   string `json:"intent_claim_pub,omitempty"`
    IntentClaimSig   string `json:"intent_claim_sig,omitempty"`
    EncryptedPayload string `json:"encrypted_payload,omitempty"`
}
```

Response (relay-server returns on error):

```go
// relay/client.go
type RelayResponse struct {
    EncryptedPayload string `json:"encrypted_payload,omitempty"`
    Error            string `json:"error,omitempty"`
}
```

Inner request payload (inside `encrypted_payload`, plugin → server):

```go
// relay/payload.go
type InnerRequestPayload struct {
    Nonce             string        `json:"nonce"`
    OuterHash         string        `json:"outer_hash"`
    ExpiresAt         int64         `json:"expires_at"`
    Stanzas           []RelayStanza `json:"stanzas"`
    EphemeralKey      string        `json:"ephemeral_key"`
    IntentClaimSecret string        `json:"intent_claim_secret,omitempty"`
}

type RelayStanza struct {
    Type string   `json:"type"`
    Args []string `json:"args"`
    Body string   `json:"body"`
}
```

Inner response payload (inside `encrypted_payload`, server → plugin):

```go
// relay/payload.go
type InnerResponsePayload struct {
    Nonce     string `json:"nonce"`
    OuterHash string `json:"outer_hash"`
    FileKey   string `json:"file_key"`
}
```

## Outer Hash Summary

> Every field in the cleartext envelope outside `encrypted_payload` MUST be included in the outer hash. See [ARCHITECTURE.md §3.5](ARCHITECTURE.md#35-outer-hash-construction).

| Direction | Formula | Example |
|---|---|---|
| Request (plugin → server) | `SHA-256("{version}.{action}.{stream}.{intent_id}.{tag}.{expires_at}.{intent_claim_pub}")` | `SHA-256("1.unwrap.0.a3f1...7b8c.QPg24g.1715350800.AAAA...")` |
| Fulfill response (server → plugin) | `SHA-256("{version}.{action}.{intent_id}")` | `SHA-256("1.fulfill.a3f1...7b8c")` |
| Reject response (server → plugin) | `SHA-256("{version}.{action}.{intent_id}")` | `SHA-256("1.reject.a3f1...7b8c")` |
